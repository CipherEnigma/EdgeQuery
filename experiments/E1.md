# E1 — Kill Test

## Purpose

E1 is the actual research question: given a limited budget of "is this edge real?"
queries, does *choosing which edge to ask about strategically* beat just asking at
random? Four strategies are compared: `random` (baseline), `structural` (shared
neighbours), `uncertainty` (model's least-confident nodes), and `oracle_voi` (tentatively
add + retrain + measure — the theoretical gold standard).

Unlike E0, E1 is allowed to fail — a null result (nothing beats random) would be a real,
reportable finding. What E1 is *not* allowed to do is fail silently because of a bug. As
it turned out, it did exactly that on the first run, and untangling why took most of the
effort documented below.

## What it runs

Script: `experiments/e1_killtest.py`

**Parameters (fixed across all three runs described below):**
- `SEEDS = [0, 1, 2]`
- `BUDGET = 20`
- `oracle_voi` is explicitly called as `partial(oracle_voi_scorer, n_sample=15, epochs=25)`
  in this script — note this is a hardcoded override, so later changes to
  `oracle_voi_scorer`'s *default* `n_sample` (see below) did not change what this script
  actually ran.

**What varied between runs:** `observe_frac` (the fraction of true edges revealed for
free before querying starts) — a `GraphEnv`/`run_multi_seed` default, changed once during
the project, plus one internal fix to how `oracle_voi_scorer` picks its 15 candidates.

**Metric:** AUC of the accuracy-vs-steps curve per strategy, then each strategy's AUC gap
vs. `random`'s AUC. Whichever has the largest positive gap is declared the "winner" and
the script prints `PURSUE`; if none is positive, it prints `PIVOT`.

## Run A — `observe_frac = 0.1`, oracle_voi using random candidate sampling

This was the original run, before any bug had been found.

```
random:      AUC mean=5.56 (+/- 0.91), final acc mean=0.296
structural:  AUC mean=6.23 (+/- 0.92), final acc mean=0.306
uncertainty: AUC mean=5.45 (+/- 0.87), final acc mean=0.306
oracle_voi:  AUC mean=5.62 (+/- 1.02), final acc mean=0.296

Gap vs random: structural +0.67 | uncertainty -0.11 | oracle_voi +0.06
Winner: structural -> PURSUE
```

**Why this was suspicious enough to investigate further:** `oracle_voi` is supposed to be
the *best possible* strategy — it doesn't guess, it directly retrains and measures the
effect of each candidate edge. It should never lose badly to a cheap heuristic like
`structural`. Getting +0.06 (barely above random) while `structural` got +0.67 was a red
flag that something was broken, not that "trying and measuring" is a bad idea.

**Diagnosis (done outside the formal script, via ad-hoc checks):** `oracle_voi_scorer`
was picking its 15 candidates to retrain-and-check **completely at random** out of ~3,991
unrevealed pairs. Since real edges are only ~3.7% of all candidates, a random sample of
15 has a substantial chance of containing *zero* real edges — so most of the time,
`oracle_voi` was just finding the "best" of a handful of non-edges, which is close to
noise.

## Run B — `observe_frac = 0.1` (unchanged), oracle_voi fixed to pre-filter candidates

**The fix applied to `src/scorers.py`:** before spending the expensive retrain budget,
first rank all unrevealed candidates using the cheap `structural_scorer` (shared-neighbour
count — no training involved, effectively free), then only retrain-and-check the
top-ranked candidates (still 15 of them here, per this script's explicit `n_sample=15`).
The idea: point the expensive check at plausible candidates instead of blind ones.

```
random:      AUC mean=5.56 (+/- 0.91), final acc mean=0.296   (unchanged, unaffected by the fix)
structural:  AUC mean=6.23 (+/- 0.92), final acc mean=0.306   (unchanged)
uncertainty: AUC mean=5.45 (+/- 0.87), final acc mean=0.306   (unchanged)
oracle_voi:  AUC mean=5.74 (+/- 0.89), final acc mean=0.296

Gap vs random: structural +0.67 | uncertainty -0.11 | oracle_voi +0.18
Winner: structural -> PURSUE
```

**Interpretation at the time:** the fix helped (`oracle_voi`'s gap roughly tripled, +0.06
→ +0.18) but nowhere near enough to catch `structural`. We traced this further (again
outside the formal script, using an exploratory `n_sample=40` — larger than what this
script actually uses — purely to make the diagnosis easier to see) and found: at
`observe_frac=0.1`, only **5 of ~3,991** candidates have *any* shared neighbours at all.
So even the "smart" pre-filtered shortlist was mostly arbitrary filler (candidates tied at
a structural score of 0, broken by array order — which is why the diagnostic kept picking
pairs involving node 0 specifically). We called this the **cold-start problem**: the
pre-filter needs existing structure to work with, and at 10% starting visibility there
isn't enough of it yet.

## Run C — `observe_frac = 0.3` (raised to fix the cold-start problem)

**The change applied:** `observe_frac`'s default was raised from 0.1 to 0.3 across
`src/env.py` and `src/loop.py`, on the theory that starting with more of the true graph
visible would give the structural pre-filter (and `structural_scorer` itself) enough
signal to be meaningfully informative from the start.

```
random:      AUC mean=10.93 (+/- 0.69), final acc mean=0.546
structural:  AUC mean=10.99 (+/- 0.72), final acc mean=0.546
uncertainty: AUC mean=10.93 (+/- 0.69), final acc mean=0.546
oracle_voi:  AUC mean=10.99 (+/- 0.71), final acc mean=0.537

Gap vs random: structural +0.06 | uncertainty +0.00 | oracle_voi +0.06
Winner: structural -> PURSUE (nominally; the gap is not meaningfully different from zero)
```

**What actually happened:** the cold-start problem went away, but a new problem replaced
it. With 30% of the real graph already given away for free, the model was already doing
well (baseline accuracy jumped from ~0.30 to ~0.55) before any querying even started —
there was barely any headroom left for *any* strategy to improve things further. All four
strategies collapsed to nearly the same result. We called this the **ceiling effect**.

## Interpretation across all three runs

None of the three single-number results from E1 should be reported as "the" finding:

- **Run A** is invalidated by the `oracle_voi` sampling bug — it understates `oracle_voi`
  unfairly.
- **Run B** is a fairer comparison but is contaminated by the cold-start problem — it's
  unclear how much of `oracle_voi`'s continued weakness is a real limitation vs. an
  artifact of having almost no structure to pre-filter on.
- **Run C** is undermined by the ceiling effect — the near-zero gaps across all strategies
  don't mean the strategies are equivalent, they mean there was almost nothing left to
  compete for.

What *is* a solid finding across all three runs: **`structural` never performed worse
than `random`, and was the only strategy to show a clear, repeatable positive gap** (Run
A and B both +0.67). That's worth carrying forward. `uncertainty` was flat-to-negative in
every run — also a real, consistent (if negative) result.

This three-run progression is what motivated E2: rather than picking one `observe_frac`
value and trusting it, sweep across several and look for where (if anywhere) a strategy's
advantage is real and not just an artifact of too little or too much starting structure.

## Known limitations / what's not covered here

- Only 3 seeds per run — the AUC standard deviations (~0.7-1.0) are similar in size to
  the gaps being compared, so none of these three runs should be treated as statistically
  confident on their own.
- `oracle_voi`'s `n_sample=15` (hardcoded in this script) was never increased to match the
  `n_sample=40` used in the exploratory diagnostics — Run B and Run C's `oracle_voi`
  numbers reflect a 15-candidate shortlist, not a 40-candidate one. This is a real,
  outstanding inconsistency between what was diagnosed and what was actually measured by
  the formal script.
- `BUDGET=20` turned out (via the later E2 investigation) to likely be too small to move
  accuracy meaningfully regardless of strategy — at this budget, `random` typically
  acquires 0-1 real edges and `structural` acquires 2-4, and a 1-3 edge difference on a
  36-node test set often isn't enough to shift accuracy by a measurable amount. This means
  even Run A and Run B's `structural` result, while directionally consistent, may be
  understating the true effect size achievable with a larger budget.
- The tie-breaking bug (ties resolved by array order via `np.argmax`, biasing toward
  low-index node pairs rather than breaking ties randomly) was identified during Run B's
  diagnosis but has not been fixed in the codebase yet.

## Status

**Retired — not currently trustworthy as a source of "the" result.** All three runs were
valuable for what they taught us (found and partially fixed a real bug; discovered the
cold-start and ceiling-effect failure modes), but none of the three single numbers above
should be cited as E1's answer. The plan going forward (see E2's status) is to rerun E1
at a validated `observe_frac` operating point with a much larger budget, tracking
real-edges-acquired-per-budget as a primary metric alongside accuracy, before treating any
number here as final.
