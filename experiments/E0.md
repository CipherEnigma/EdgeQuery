# E0 — Sanity Check

## Purpose

E0 does not test whether any acquisition strategy is *good*. It tests whether the
pipeline itself is *honest* — that it runs end-to-end across multiple random seeds
without crashing, without leaking information it shouldn't have access to, and without
producing results so broken (e.g. a strategy collapsing accuracy toward zero) that any
later comparison (E1, E2) couldn't be trusted.

E0 must pass before any result from E1 or E2 is treated as meaningful. If E0 failed, a
weak or surprising E1/E2 result could just as easily be a bug as a real finding — E0
rules that ambiguity out.

## What it runs

Script: `experiments/e0_sanity.py`

**Strategies compared:** `random_scorer` (picks candidate edges uniformly at random —
the simplest possible baseline) vs. `uncertainty_scorer` (picks the candidate edge whose
two endpoints the model is currently most unsure about, via prediction entropy).

**Parameters:**
- `SEEDS = [0, 1, 2, 3, 4]` — 5 independent runs, varying environment/model
  initialization (the underlying graph itself is fixed, generated once with
  `make_csbm(seed=0)`).
- `BUDGET = 40` — each run spends 40 queries (asks about 40 candidate edge pairs) before
  stopping.
- `observe_frac` — how much of the true graph is revealed for free before any querying
  starts. This is a `GraphEnv` default, not set explicitly in the E0 script, so it always
  uses whatever `src/env.py` / `src/loop.py` currently default to. **This value changed
  partway through the project** (see Results below) — E0 was run once at each setting.

**Procedure, per seed:**
1. Build a `GraphEnv` around the fixed true graph (90 nodes, 3 classes, 148 real edges),
   revealing `observe_frac` of the true edges upfront.
2. Run the acquisition loop (`run_loop`) for that strategy: train a fresh GCN on the
   currently-observed graph, record test accuracy, score all remaining candidate edges,
   reveal the best-scoring one, repeat until the 40-query budget is spent.
3. Record the accuracy curve (accuracy at every one of the 41 steps: before any querying,
   then after each of the 40 queries).

**Metric:** `auc()` — the area under that accuracy-vs-steps curve, summarizing "how good
was this strategy across the whole budget-spending process," not just at the final step.

**Pass condition (the actual sanity check):** the script asserts
`uncertainty_final_accuracy >= random_final_accuracy - 0.05` — i.e., uncertainty is not
allowed to be *dramatically* worse than random. E0 is not asserting uncertainty should
win; a near-tie is an acceptable, expected outcome.

## Results

### Run 1 — `observe_frac = 0.1` (10% of true edges revealed upfront; original default)

```
random:      AUC mean=12.14 (+/- 1.86), final acc mean=0.333
uncertainty: AUC mean=11.83 (+/- 1.85), final acc mean=0.306
```

Passed. Random and uncertainty came out close to tied (uncertainty very slightly lower,
well within the 0.05 tolerance).

### Run 2 — `observe_frac = 0.3` (30% of true edges revealed upfront; current default)

After the cold-start problem was diagnosed in E1 (see `notes.md` Part 12 / E1 writeup),
`observe_frac`'s default was raised from 0.1 to 0.3 across the whole codebase, and E0 was
rerun under the new setting for consistency:

```
random:      AUC mean=21.56 (+/- 2.39), final acc mean=0.539
uncertainty: AUC mean=21.45 (+/- 2.37), final acc mean=0.533
```

Passed. Again close to tied. Both accuracy and AUC are much higher than Run 1 simply
because far more of the true graph is visible for free before any querying begins — not
because either strategy got smarter.

For reference, the accuracy ceiling (training on the *entire* true graph, no hiding at
all) is roughly 0.69–0.75 depending on seed (measured later, in the E2 sweep's
`full_graph_accuracy` calculation) — so Run 2's ~0.54 final accuracy, reached after only
40 queries on top of a 30%-revealed graph, is already most of the way to that ceiling.

## Interpretation

- **The pipeline is honest.** Across both parameter settings and 5 seeds each, nothing
  crashed, no strategy collapsed, and the sanity bound held. This is exactly what E0 is
  for, and it did its job both times.
- **E0 cannot and does not tell you which strategy is better.** The near-tie between
  random and uncertainty in both runs is not evidence that uncertainty doesn't work —
  it's simply outside what this check was designed to measure. That question belongs to
  E1 (structural and oracle_voi weren't even tested here) and, more rigorously, to E2.
- **The two runs are not comparable to each other as a "result."** They used different
  `observe_frac` values, so the jump from ~0.33 to ~0.54 final accuracy reflects a
  changed starting condition, not an improvement in either strategy. Only Run 2 reflects
  the codebase's current defaults.

## Known limitations / what's not covered here

- E0 only tests `random` vs `uncertainty`. `structural` and `oracle_voi` are exercised
  for the first time in E1, not E0 — a bug specific to either of those (like the
  candidate-sampling bug found in `oracle_voi_scorer`) would not be caught by E0.
- E0's pass condition is deliberately loose (a 0.05 tolerance band) — it's built to catch
  outright breakage, not subtle problems. The `oracle_voi` sampling bug and the
  cold-start / ceiling-effect issues found later in E1/E2 are examples of real problems
  that E0's check would not have flagged, by design.
- Only 5 seeds. Fine for a binary "did it break" check; not enough to make any
  statistical claim about effect sizes (that concern applies to E1/E2, not E0).

## Status

**Done.** No further action planned for E0 itself — it has served its purpose (confirming
the harness is trustworthy) at both `observe_frac` settings tested so far. Future changes
to the pipeline (e.g. fixing the tie-breaking bug, or budget/scale changes for the
upcoming bigger-budget E1 rerun) should be re-verified against E0 before trusting any new
E1/E2 numbers built on top of them.
