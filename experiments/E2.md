# E2 — observe_frac Sweep

## Purpose

E1 ran into two opposite failure modes depending on one setting (`observe_frac`, how much
of the true graph is revealed for free before any querying starts):

- Too low (0.1): a **cold-start problem** — almost no candidate edges have any structural
  signal to work with, so even the "smart" strategies were picking close to blind.
- Too high (0.3): a **ceiling effect** — so much of the graph is already visible that
  there's barely any accuracy headroom left for any strategy to improve on.

E2's purpose was to stop guessing at a single `observe_frac` value and instead sweep
across several, to find out whether there's a middle zone where a strategy's advantage is
real — enough structure to work with, and enough headroom left to show it — rather than
picking one number and hoping it landed in the right place.

## What it runs

Script: `experiments/e2_observe_frac_sweep.py`

**Parameters:**
- `OBSERVE_FRACS = [0.05, 0.10, 0.15, 0.20, 0.30]` — the values swept.
- `SEEDS = [0, 1, 2]`
- `BUDGET = 15`
- `oracle_voi` called with `n_sample=40, epochs=25` (note: this is a *different*
  `n_sample` than E1's formal script used, which was hardcoded to 15 — see E1.md's
  "Known limitations" for that discrepancy).

**The metric — `normalized_advantage`:** raw accuracy or AUC isn't fair to compare across
different `observe_frac` values, because the amount of achievable headroom is different at
each one. So for every run, we also compute `full_graph_accuracy` — what accuracy would be
if the model got the *entire* true graph for free (this only depends on the fixed
train/test split for that seed, not on `observe_frac`, so it's computed once per seed and
reused across the whole sweep). Then:

```
normalized_advantage = (final_accuracy - observed_accuracy) / (full_graph_accuracy - observed_accuracy)
```

i.e. "what fraction of the *possible* accuracy gap (from where you started to the true
ceiling) did this strategy's budget-spending actually close." 1.0 = reached the ceiling
using only the budget; 0.0 = no progress; can go negative if a strategy's picks actively
hurt.

**Procedure:** for each `observe_frac` value, for each of the 4 strategies, for each seed:
build a fresh `GraphEnv`, run the 15-query loop, compute `normalized_advantage`. Average
across seeds. Then compute each strategy's *excess* normalized advantage over `random` at
that `observe_frac`, to isolate the strategy's own contribution from how much headroom
happened to exist.

## Results

**Full-graph accuracy ceiling per seed** (the reference used in the normalization):
`{seed 0: 0.694, seed 1: 0.750, seed 2: 0.694}`

**Normalized advantage, mean across 3 seeds:**

| observe_frac | random | structural | uncertainty | oracle_voi |
|---|---|---|---|---|
| 0.05 | 0.000 | 0.093 | -0.026 | 0.085 |
| 0.10 | 0.063 | 0.165 | 0.020 | 0.065 |
| 0.15 | 0.000 | -0.041 | 0.000 | 0.000 |
| 0.20 | 0.000 | 0.000 | 0.056 | 0.037 |
| 0.30 | 0.000 | 0.048 | 0.000 | 0.048 |

**Excess normalized advantage vs. random** (the number we were actually hoping would show
a clean "hump" — rising then falling as `observe_frac` increases):

| observe_frac | structural | uncertainty | oracle_voi |
|---|---|---|---|
| 0.05 | +0.093 | -0.026 | +0.085 |
| 0.10 | +0.102 | -0.043 | +0.003 |
| 0.15 | **-0.041** | 0.000 | 0.000 |
| 0.20 | 0.000 | +0.056 | +0.037 |
| 0.30 | +0.048 | 0.000 | +0.048 |

## Interpretation, part 1 — this is not a hump

A real inverted-U shape should rise smoothly, peak, and fall smoothly. Instead,
`structural`'s excess advantage goes +0.093 → +0.102 → **-0.041** → 0.000 → +0.048: up,
up, negative, flat, up again. A dip below zero in the middle, followed by recovery, is not
what a genuine underlying effect looks like — it's what noise looks like. Seven of the
fifteen cells in the normalized-advantage table are exactly `0.000`, which specifically
means "final accuracy was numerically identical to starting accuracy" across all 3 seeds
for that cell — a strong hint that the measurement, not the effect, is flat.

## Interpretation, part 2 — the actual root cause (found by a follow-up diagnostic)

Rather than trust the sweep's shape, we measured directly how many **real edges** each
strategy actually acquires within a 15-query budget (a separate, non-formal diagnostic
script, 5 seeds, budget=15, `random`/`structural`/`uncertainty` only — `oracle_voi`
excluded for cost):

Test set size: 36 nodes → one single additional correctly-classified node changes
accuracy by 1/36 ≈ **0.0278 (2.78 percentage points)** — that's the smallest possible
unit of movement this metric can register.

Real edges acquired per 15-query budget (mean across 5 seeds):

| observe_frac | random | structural | uncertainty |
|---|---|---|---|
| 0.05 | 0.2 | **2.8** | 0.6 |
| 0.10 | 0.8 | **2.2** | 0.6 |
| 0.20 | 0.0 | **1.0** | 0.2 |
| 0.30 | 0.2 | **1.6** | 0.4 |

**This is the real finding, and it's a clean one:** `structural` consistently acquires
3-14x more real edges than `random`, at every `observe_frac` tested, on every seed. That's
not noise — it's a large, reproducible effect on the thing the strategies are actually
being asked to do (find real edges).

**But it's invisible to the accuracy-based metric**, because a 1-3 edge difference, added
on top of a graph that already has 14-44 edges, essentially never crosses the 2.78%
resolution floor of a 36-node test set. The E2 sweep wasn't measuring "does being smart
help" — it was measuring "does being smart help *by enough to move a coarse, low-budget
accuracy readout*," and the answer to that narrower question was "usually not enough to
tell," independent of `observe_frac`. The apparent noise in the hump-shaped table is a
direct consequence of this resolution problem, not evidence that the strategies don't
differ.

## Known limitations / what's not covered here

- `oracle_voi` was excluded from the follow-up hit-rate diagnostic (too expensive to run
  at 5 seeds) — we only have its normalized-advantage numbers from the original sweep,
  not a hit-rate breakdown to explain them the same way.
- The follow-up diagnostic used 5 seeds vs. the sweep's 3 — not a like-for-like
  re-verification of the sweep itself, just a targeted check of the mechanism.
- `BUDGET=15` was inherited from a size that made sense for E1's cost constraints, not
  chosen to guarantee accuracy could resolve the effect — that mismatch is precisely what
  this experiment exposed.
- We have not yet re-run the sweep (or E1) at a budget large enough to confirm the
  hit-rate advantage actually does translate into a real accuracy gap once given enough
  queries to compound.

## Status

**Diagnostic complete; primary sweep result (the hump) retracted as noise, but a real,
strong, reproducible effect (structural's edge-acquisition hit-rate) was found underneath
it.** This changes the project's evaluation approach going forward:

1. **Track real-edges-acquired-per-budget as a primary metric**, not just downstream
   accuracy — it has far higher resolution and is where the actual strategy differences
   live.
2. **Re-run with a much larger budget** (~200 queries instead of 15) so that structural's
   per-query hit-rate advantage has room to compound into an edge-count gap large enough
   for accuracy to detect (e.g. ~30 real edges vs. ~10 — comparable to the 14→148 edge
   range that took accuracy from ~22% to ~71% in the original headroom check).
3. `oracle_voi` will need its own, separately-scoped rerun (smaller budget or fewer seeds)
   given its per-candidate retrain cost — bundling it into a 200-query sweep across all
   `observe_frac` values is not practical.
